# 前端：工作流配置、部署激活与设备运行模式说明

更新日期：2026-08-03

## 1. 文档目的

本文用于前端实现项目级正式工作流的完整配置链路：

```text
配置任务工作流
  → 绑定正式 Boolean 结果变量
  → 发布冻结快照
  → 激活部署
  → 切换设备运行模式
  → 手动、周期或 PLC 握手触发正式运行
  → 查询运行结果
```

本文以当前后端实际实现为准。对于已有接口但尚不能形成完整业务闭环的功能，会明确标记为“当前缺口”。

## 2. 三组概念不能混用

| 概念 | 作用 | 当前类型 |
|---|---|---|
| 设备运行模式 | 决定设备用于生产、手动操作还是检修 | `DeviceRunMode` |
| 项目任务触发类型 | 决定项目运行是立即执行还是周期执行 | `WorkflowProjectTaskType` / `WorkflowProjectRunStartType` |
| 工作流调试执行模式 | IDE 内单次运行、单步调试或指定次数循环 | `WorkflowExecutionMode` |

设备运行模式不等于工作流触发类型。例如：

- 设备处于 `Auto`，项目任务仍可以配置为立即或周期触发；
- `DebugStep` 是 IDE 调试模式，不能替代正式部署运行；
- PLC 握手触发只在设备处于生产状态时生效。

## 3. 前端推荐配置流程

### 3.1 第一步：配置项目任务

调用：

```http
GET /api/app/workflow/projects/{projectId}/tasks
PUT /api/app/workflow/projects/tasks
```

前端需要配置：

1. 启用哪些工作流；
2. 工作流执行顺序；
3. 项目任务触发类型；
4. 周期触发时的间隔；
5. 最终判定工作流；
6. 最终 Boolean 输出变量。

### 3.2 第二步：发布部署快照

调用：

```http
POST /api/app/workflow/projects/{projectId}/deployments
```

发布会冻结：

- 已启用工作流及执行顺序；
- 工作流图；
- 已生成的脚本源码和程序哈希；
- 项目变量定义及默认值。

运行时使用冻结快照，不直接使用发布之后继续修改的工作流草稿。

### 3.3 第三步：激活部署

调用：

```http
POST /api/app/workflow/deployments/{deploymentId}/activate
```

只有激活部署才能创建正式项目运行。配置或工作流发生变化后，需要重新发布并激活。

### 3.4 第四步：准备设备生产状态

正式 OPC UA 握手要求：

```text
DeviceStatus == Running
并且
DeviceRunMode == Online 或 Auto
```

还必须同时满足：

- 项目存在激活部署；
- 项目不存在 `Queued` 或 `Running` 的活动运行；
- 已配置正式结果工作流和 Boolean 输出变量；
- OPC UA 握手已启用且当前阶段为空闲。

## 4. 项目任务配置接口

### 4.1 数据类型

```ts
export enum WorkflowProjectTaskType {
  Immediate = 0,
  Cyclic = 1,
}

export interface ProjectTaskBatch {
  projectId: string
  taskType: WorkflowProjectTaskType
  cycleIntervalSeconds?: number | null
  resultWorkflowId?: string | null
  resultVariableName?: string | null
  items: ProjectTaskItem[]
}

export interface ProjectTaskItem {
  id: string
  projectId: string
  workflowId: string
  workflowName: string
  isEnabled: boolean
  orderNo: number
}
```

### 4.2 获取任务配置

```http
GET /api/app/workflow/projects/{projectId}/tasks
```

响应包含当前项目的全部工作流。尚未配置为任务的工作流也会返回，但：

```json
{
  "id": "00000000-0000-0000-0000-000000000000",
  "isEnabled": false,
  "orderNo": 0
}
```

### 4.3 保存任务配置

```http
PUT /api/app/workflow/projects/tasks
Content-Type: application/json
```

请求示例：

```json
{
  "projectId": "3a22ce72-c2d4-7b10-7862-814a3c14b91f",
  "taskType": 0,
  "cycleIntervalSeconds": null,
  "resultWorkflowId": "11111111-2222-3333-4444-555555555555",
  "resultVariableName": "inspectionPassed",
  "items": [
    {
      "id": "00000000-0000-0000-0000-000000000000",
      "projectId": "3a22ce72-c2d4-7b10-7862-814a3c14b91f",
      "workflowId": "11111111-2222-3333-4444-555555555555",
      "workflowName": "正式检测流程",
      "isEnabled": true,
      "orderNo": 0
    }
  ]
}
```

后端校验规则：

- 至少包含一条任务配置；
- `WorkflowId` 不能为空、不能重复，且必须属于当前项目；
- `Cyclic` 模式必须提供大于 0 的 `cycleIntervalSeconds`；
- 结果工作流必须处于启用状态；
- 结果变量必须是所选工作流声明的正式输出；
- 结果变量声明类型必须为 `System.Boolean`。

前端保存成功后，必须使用响应覆盖本地对象：

```ts
taskConfig.value = await updateProjectTasks(taskConfig.value)
```

## 5. 部署接口

基础地址：

```text
/api/app/workflow
```

### 5.1 部署状态

```ts
export enum WorkflowProjectDeploymentStatus {
  Draft = 0,
  Published = 1,
  Activated = 2,
  Archived = 3,
}
```

| 状态 | 含义 | 当前正常来源 |
|---|---|---|
| `Draft` | 草稿部署 | 当前发布流程不会创建该状态 |
| `Published` | 已发布、尚未激活 | 首次发布 |
| `Activated` | 当前正式运行版本 | 激活成功 |
| `Archived` | 被其他部署替换的历史版本 | 当前单部署模型通常无法形成 |

### 5.2 部署 DTO

```ts
export interface ProjectDeployment {
  id: string
  projectId: string
  revision: number
  status: WorkflowProjectDeploymentStatus
  isCurrentActive: boolean
  canActivate: boolean
  canReactivate: boolean
  canRollback: boolean
  snapshotHash: string
  itemCount: number
  activatedAt?: string | null
  activatedBy?: string | null
  creationTime: string
}
```

前端当前 `ProjectDeployment` 类型缺少 `itemCount`、`activatedAt`、`activatedBy` 和 `creationTime`，建议补齐。

### 5.3 获取当前部署

```http
GET /api/app/workflow/projects/{projectId}/deployments
```

注意：尽管路径名为 `deployments`，当前响应是**单个对象**，不是数组。接口返回按修订号倒序的最新部署。

尚未发布时返回业务错误：

```text
当前项目尚未创建部署快照。
```

前端应将此错误转换为“尚未发布”，不显示全局错误页。

### 5.4 发布部署

```http
POST /api/app/workflow/projects/{projectId}/deployments
```

发布前置条件：

- 至少有一个已启用工作流；
- 所有启用工作流仍然存在；
- 工作流已经迁移并保存为脚本程序；
- `SourceCode` 和 `ProgramHash` 均有效。

失败示例：

```text
当前项目没有已启用的工作流任务，无法发布部署快照。
工作流“正式检测流程”尚未迁移为脚本程序，不能发布部署；请先执行迁移并重新保存。
```

### 5.5 激活部署

```http
POST /api/app/workflow/deployments/{deploymentId}/activate
```

支持 `Published` 和 `Archived` 状态。目标已经激活时按幂等操作返回当前部署。

### 5.6 重新激活

```http
POST /api/app/workflow/deployments/{deploymentId}/reactivate
```

当前允许状态：

- `Published`；
- `Archived`；
- `Activated`。

目标已经激活时直接返回，不重新创建部署。

### 5.7 回滚

```http
POST /api/app/workflow/deployments/{deploymentId}/rollback
```

只允许回滚到 `Published` 或 `Archived` 部署。不能把当前激活部署作为回滚目标。

当前限制：获取接口不返回历史列表，重复发布也不会创建新修订，因此前端目前没有可展示和选择的历史回滚目标。

### 5.8 删除部署

```http
DELETE /api/app/workflow/deployments/{deploymentId}
```

以下情况禁止删除：

- 部署处于 `Activated`；
- 部署仍被 `Queued` 或 `Running` 的运行引用。

## 6. 前端部署交互建议

### 6.1 当前可直接实现

配置抽屉建议显示：

```text
部署状态：未发布 / 已发布 / 已激活
版本：rev {revision}
工作流数量：{itemCount}
快照哈希：{snapshotHash}
激活时间：{activatedAt}
```

按钮规则：

| 按钮 | 显示条件 | 调用 |
|---|---|---|
| 发布快照 | 已成功保存任务配置 | `POST projects/{projectId}/deployments` |
| 激活 | `canActivate` | `POST deployments/{id}/activate` |
| 重新激活 | `canReactivate` | `POST deployments/{id}/reactivate` |
| 删除 | 非激活状态 | `DELETE deployments/{id}` |
| 回滚 | 暂不展示 | 缺少历史部署列表 |

不要把发布和激活视为同一个原子操作。推荐拆成两个步骤，让用户可以看到发布成功但激活失败的状态。

如果产品仍保留“一键发布并激活”，必须分别处理错误：

```ts
const published = await publishProjectDeployment(projectId)
try {
  deployment.value = await activateProjectDeployment(published.id)
} catch (error) {
  deployment.value = published
  toast.error('快照已发布，但激活失败，请重试激活。')
}
```

### 6.2 配置脏状态

以下操作完成后应标记“需要重新发布”：

- 修改任务启用状态；
- 修改任务顺序；
- 修改任务触发方式或周期；
- 修改最终结果绑定；
- 修改工作流图或脚本；
- 修改项目变量定义或默认值。

当前部署 DTO 没有直接返回“草稿是否不同于激活快照”。前端可以在本地修改后显示提示，但刷新页面后无法可靠恢复该判断。

## 7. 正式项目运行

### 7.1 运行启动类型

```ts
export enum WorkflowProjectRunStartType {
  Immediate = 0,
  Cyclic = 1,
}

export enum WorkflowProjectRunOnErrorAction {
  StopRun = 0,
  ContinueRun = 1,
}
```

正式运行创建接口：

```http
POST /api/app/workflow/runs
Content-Type: application/json
```

建议前端类型：

```ts
export interface EnqueueProjectRunInput {
  projectId: string
  name: string
  startType: WorkflowProjectRunStartType
  cycleIntervalSeconds?: number | null
  onErrorAction: WorkflowProjectRunOnErrorAction
}
```

`name` 必填且最长 128 个字符。周期启动必须提供 1～86400 秒的周期。同一项目存在 `Queued` 或 `Running` 运行时，后端拒绝重复创建。

### 7.2 运行查询与取消

```http
GET  /api/app/workflow/runs?projectId={projectId}&skipCount=0&maxResultCount=20
GET  /api/app/workflow/runs/{runId}
POST /api/app/workflow/runs/{runId}/cancel
```

项目运行状态：

```ts
export enum WorkflowProjectRunStatus {
  Queued = 0,
  Running = 1,
  Succeeded = 2,
  Failed = 3,
  Canceled = 4,
}
```

### 7.3 当前前端缺口

当前 `workflow.ts` 已有运行列表、详情和取消接口，但缺少 `POST /runs` 的创建运行封装，页面也没有正式运行的“立即启动/周期启动”入口。

任务配置页面虽然能保存 `Immediate/Cyclic`，但该字段本身不会让前端自动创建运行。前端需要补充运行创建入口，或明确正式运行仅由 PLC 握手等外部触发源创建。

## 8. 设备状态和运行模式

### 8.1 设备运行模式

```ts
export enum DeviceRunMode {
  Online = 0,
  Auto = 1,
  Manual = 2,
  Maintenance = 3,
}
```

| 模式 | 中文 | 主要用途 | 正式 PLC 握手 |
|---|---|---|---|
| `Online` | 联机 | 上位机或 MES 远程控制 | 允许 |
| `Auto` | 自动 | 本地自动生产流程 | 允许 |
| `Manual` | 手动 | 操作人员单步调试设备 | 禁止 |
| `Maintenance` | 检修 | 专业维护和参数调整 | 禁止 |

相机、投影、运动、串口、PLC 等人工硬件控制通常只允许在 `Manual` 或 `Maintenance` 模式执行。

### 8.2 设备状态

```ts
export enum DeviceStatus {
  Standby = 0,
  Starting = 1,
  Running = 2,
  Paused = 3,
  Stopping = 4,
  Stopped = 5,
  Resetting = 6,
  FaultAcknowledging = 7,
  Fault = 8,
  EmergencyStop = 9,
  Initializing = 10,
}
```

前端枚举、中文标签和状态徽标已经覆盖以上全部 11 种状态。

### 8.3 获取状态与切换模式

```http
GET  /api/app/device-state/current-state
POST /api/app/device-state/switch-mode
```

切换请求：

```json
{
  "newMode": 1,
  "reason": "切换到自动生产"
}
```

`DeviceStateDto`：

```ts
export interface DeviceStateDto {
  status: DeviceStatus
  runMode: DeviceRunMode
  currentFaultId: string | null
  currentFaultLevel: number | null
  currentFaultCode: string | null
  isInTransition: boolean
  canAcceptProductionCommand: boolean
  canSwitchMode: boolean
}
```

前端应以服务端返回的 `canSwitchMode` 控制模式选择器。当前规则是：

```text
非过渡状态
并且
DeviceStatus 为 Standby 或 Stopped
```

不要只根据 `runMode` 判断是否允许切换。

### 8.4 状态与操作矩阵

| 设备状态/模式 | 切换模式 | 人工硬件调试 | OPC UA 正式握手 |
|---|---:|---:|---:|
| `Standby + 任意模式` | 允许 | 仅 Manual/Maintenance | 禁止 |
| `Stopped + 任意模式` | 允许 | 仅 Manual/Maintenance | 禁止 |
| `Running + Online` | 禁止 | 禁止 | 允许 |
| `Running + Auto` | 禁止 | 禁止 | 允许 |
| `Running + Manual` | 禁止 | 取决于具体操作会话 | 禁止 |
| `Running + Maintenance` | 禁止 | 取决于具体操作会话 | 禁止 |
| 过渡状态 | 禁止 | 禁止或只读 | 禁止 |
| `Fault/EmergencyStop` | 禁止 | 禁止或故障处理 | 禁止 |

## 9. 设备运行模式覆盖检查

### 9.1 已覆盖

| 能力 | 后端 | 前端 |
|---|---:|---:|
| Online | 已实现 | 已实现 |
| Auto | 已实现 | 已实现 |
| Manual | 已实现 | 已实现 |
| Maintenance | 已实现 | 已实现 |
| 四种模式中文标签 | 已实现 | 已实现 |
| 当前状态查询 | 已实现 | 已实现 |
| 模式切换 | 已实现 | 已实现 |
| `canSwitchMode` 禁用控制 | 已实现 | 已实现 |
| SignalR 状态更新 | 已实现 | 已实现 |
| 11 种设备状态展示 | 已实现 | 已实现 |

结论：**运行模式枚举及显示覆盖完整。**

### 9.2 未形成完整闭环

当前公开的 `IDeviceStateAppService` 只有：

- 查询当前状态；
- 查询当前故障；
- 切换运行模式；
- 查询故障和状态日志。

底层 `IDeviceStateManager` 虽然具有启动、暂停、恢复、停止、复位和故障确认能力，但没有对应的应用服务接口和前端控制入口。

因此前端目前不能独立完成：

```text
Standby → Starting → Running
Running → Paused → Running
Running → Stopping → Stopped
Fault/EmergencyStop → Resetting → Standby
```

结论：**模式枚举覆盖完整，但设备生产状态控制未覆盖完整。** 如果设备状态没有由 PLC、硬件按钮或其他后台服务推进到 `Running`，OPC UA 握手会一直不接受生产请求。

## 11. 部署管理覆盖检查

| 能力 | 后端接口 | 前端 API | 当前页面 |
|---|---:|---:|---:|
| 获取最新部署 | 已实现 | 已实现 | 已使用 |
| 发布 | 已实现 | 已实现 | 已使用 |
| 激活 | 已实现 | 已实现 | 已使用 |
| 重新激活 | 已实现 | 已实现 | 未使用 |
| 回滚 | 已实现 | 已实现 | 未使用 |
| 删除 | 已实现 | 已实现 | 未使用 |
| 历史部署列表 | 未实现 | 未实现 | 未实现 |
| 新修订版本生成 | 未实现 | 不适用 | 不适用 |

当前发布语义是：

- 首次发布创建 `revision=1`；
- 后续发布原地更新最新部署；
- 不创建新的修订记录；
- 获取接口只返回最新单条部署。

因此重新激活可以用于当前部署，回滚和历史删除虽然存在接口，但缺少可供前端选择的历史版本。

## 12. 建议补齐顺序

### P0：保证正式生产可启动

1. 明确由谁把设备状态推进到 `Running`；
2. 如果由前端控制，后端增加设备启动、暂停、恢复、停止、复位和故障确认接口；
3. 前端根据服务端能力字段显示设备状态控制按钮。

### P1：补齐正式运行入口

1. 前端增加 `enqueueProjectRun`；
2. 提供立即运行和周期运行表单；
3. 显示活动运行并阻止重复提交；
4. 保留 PLC 握手作为独立的外部触发方式。

### P2：补齐部署生命周期

1. 后端发布时创建新修订，而不是覆盖旧部署；
2. 增加分页历史部署接口；
3. 前端增加版本列表、激活、回滚和删除操作；
4. 显示版本差异、激活人和激活时间。

## 13. 前端错误处理

| 后端错误 | 前端处理 |
|---|---|
| 当前项目尚未创建部署快照 | 显示“尚未发布”，引导发布 |
| 当前项目没有已启用的工作流任务 | 定位到任务配置第一步 |
| 工作流尚未迁移为脚本程序 | 引导重新保存或迁移工作流 |
| 当前项目没有已激活的部署快照 | 引导激活已发布部署 |
| 启用 OPC UA 握手前必须配置正式任务的布尔结果变量 | 定位到正式结果绑定 |
| 当前状态不允许切换运行模式 | 刷新设备状态并显示服务端原因 |
| 同一项目已有活动运行 | 刷新运行列表，不重复创建 |
| 当前激活部署不允许删除 | 隐藏删除按钮并说明原因 |

前端必须优先展示 ABP 业务错误消息，不要只显示 HTTP 状态码。

## 14. 验收用例

### 14.1 任务与部署

1. 未启用任何工作流时不能发布。
2. 周期任务没有有效周期时不能保存。
3. 非 Boolean 结果变量不能保存为正式结果绑定。
4. 发布成功但激活失败时，页面保留“已发布”状态。
5. 激活成功后显示部署版本、哈希和激活信息。
6. 修改任务或工作流后显示“需要重新发布”。

### 14.2 设备模式

1. 模式选择器显示联机、自动、手动和检修四种模式。
2. `canSwitchMode=false` 时选择器禁用。
3. `Standby/Stopped` 且 `canSwitchMode=true` 时允许切换。
4. `Running + Online/Auto` 时 OPC UA 握手可以进入生产流程。
5. `Running + Manual/Maintenance` 时 OPC UA 握手不创建运行。
6. 过渡、故障和急停状态不能接受生产请求。

### 14.3 正式运行

1. 没有激活部署时不能创建正式运行。
2. Immediate 创建一次运行。
3. Cyclic 必须携带有效周期。
4. 同一项目存在活动运行时禁止重复创建。
5. 取消运行后状态更新为 `Canceled`。
6. PLC 握手触发与前端主动触发使用同一激活部署快照。
