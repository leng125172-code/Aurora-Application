# 第三方工作流前端接口变更说明

> 更新时间：2026-07-29
>
> 接口前缀：`/api/app/workflow`
>
> TypeScript 客户端：`Sources/AuroraStruct3D/AuroraStruct3D.Frontend/src/api/workflow.ts`

## 1. 变更概述

工作流后端已调整为“GraphData 负责编辑、已保存程序负责执行”的模式。

第三方前端仍通过 `GraphData` 创建和编辑工作流，不需要处理工作流伪代码。新增独立的 `workflow.ts` 客户端作为第三方稳定入口，包含：

- 工作流 CRUD、校验、模拟和输出路径查询。
- 已保存工作流的画布级调试、断点、单步和状态查询。
- 单工作流正式执行及状态查询。
- 项目运行查询和取消。
- 项目任务配置。
- 项目部署、激活、重新激活、回滚和删除。

以下能力不属于第三方接口：

- `SourceCode`、脚本转换和语言服务。
- 草稿和源码历史版本。
- Monaco 编辑器能力。
- 调试未保存脚本的 `POST /api/app/workflow/source/debug`。
- `/api/app/workflow/source/*` 下的诊断、补全、格式化等代码编辑器接口。

第三方前端只操作工作流和 GraphData。调试时使用已保存工作流入口
`POST /api/app/workflow/{workflowId}/source/debug-run`，不读取、不展示也不提交源码。

完整页面交互、单步动画和 SignalR 对接见
[第三方工作流完整交互与调试对接方案](./第三方工作流完整交互与调试对接方案.md)。

## 2. 接入方式

项目内前端直接引用：

```ts
import {
    createWorkflow,
    executeWorkflow,
    getExecutionStatus,
    getOutputPaths,
    type WorkflowGraph,
} from '@/api/workflow'
```

独立第三方项目可以复制 `workflow.ts` 的类型和方法，并将其中的 `httpClient` 替换为自身 Axios 实例。请求需要沿用平台现有的认证信息和 JSON 请求头。

## 3. GraphData 数据结构

```ts
export interface WorkflowGraph {
    nodes: Array<Record<string, unknown> & {
        id: string
        type: string
    }>
    edges: Array<Record<string, unknown> & {
        id: string
    }>
}

export interface WorkflowPayload {
    projectId: string
    name: string
    graphData: WorkflowGraph
}
```

节点和边允许携带算子参数、端口、坐标、文本、条件分支和容器子图等扩展字段。第三方前端应保留无法识别的字段，避免读取后再次保存时丢失工作流信息。

### 3.1 结束节点输出配置

结束节点不能只保存“是否勾选”。每个选中变量需要保存稳定端口键、变量名称和可选
Display 名称：

```json
{
  "id": "end",
  "type": "end-node",
  "properties": {
    "inputBindings": {
      "output1": "inspection_status",
      "output2": "result_blob_key"
    },
    "inputBindingSources": {
      "output1": "variable",
      "output2": "variable"
    },
    "inputBindingDisplayNames": {
      "output1": "检测状态",
      "output2": "结果文件"
    }
  }
}
```

`inputBindingDisplayNames` 与 `inputBindings` 使用相同端口键。Display 名称允许为空；
为空或不存在时，服务端返回变量名称。文件、图片和点云应先通过存 Blob 算子得到
Blob Key，再把 Blob Key 变量绑定到结束节点。

## 4. 工作流接口

| 客户端方法 | HTTP | 路径 | 说明 |
|---|---|---|---|
| `listWorkflows(projectId)` | GET | `/api/app/workflow?projectId={projectId}` | 查询项目工作流 |
| `getWorkflow(id)` | GET | `/api/app/workflow/{id}` | 查询工作流及 GraphData |
| `createWorkflow(payload)` | POST | `/api/app/workflow` | 创建工作流 |
| `updateWorkflow(id, payload)` | PUT | `/api/app/workflow/{id}` | 更新工作流 |
| `deleteWorkflow(id)` | DELETE | `/api/app/workflow/{id}` | 删除工作流 |
| `validateWorkflow(id)` | POST | `/api/app/workflow/{id}/validate` | 校验已保存工作流 |
| `simulateWorkflow(id)` | POST | `/api/app/workflow/{id}/simulate` | 模拟已保存工作流 |
| `getOutputPaths(id, variableName)` | GET | `/api/app/workflow/{id}/output-paths?variableName={name}` | 查询模板可用输出路径 |

创建示例：

```ts
const workflow = await createWorkflow({
    projectId,
    name: '检测流程',
    graphData: {
        nodes: [
            { id: 'start', type: 'start-node' },
            { id: 'detect', type: 'operator-node' },
            { id: 'end', type: 'end-node' },
        ],
        edges: [],
    },
})
```

保存时，服务端会完成 GraphData 校验、生成受限 C# 风格脚本、计算哈希并预编译程序。第三方不需要提交或保存 `SourceCode`。

## 5. 输出路径下探

`getOutputPaths` 用于取得可直接用于模板渲染的变量路径。

假设结束节点返回变量 `retstatus`，其结构包含 `status` 和 `regions`，接口可以返回：

```text
retstatus
retstatus.status
retstatus.regions
retstatus.regions[0].name
```

数组路径同时区分：

- 实例路径：`retstatus.regions[0].name`
- Schema 路径：`retstatus.regions[].name`

每个路径项可能包含以下信息：

| 字段 | 说明 |
|---|---|
| `path` | 实例访问路径 |
| `schemaPath` | Schema 路径 |
| `type` | 值类型 |
| `nullable` | 是否允许空值 |
| `isArray` | 是否为数组 |
| `description` | 字段说明 |
| `templateAvailable` | 是否可直接用于模板 |

前端渲染前应处理可空字段；数组 Schema 路径用于选择字段，实际渲染时应使用带下标的实例路径。

## 6. 正式运行接口

### 6.1 执行单个工作流

```ts
const result = await executeWorkflow({
    projectId,
    workflowId,
    mode: 0,
    loopCount: 1,
    inputVariableKeys: [],
    outputVariableNames: ['retstatus.status'],
})
```

请求：

```http
POST /api/app/workflow/executions
```

正式运行使用：

- `0`：单次完整执行（RunOnce）。
- `2`：按照 `loopCount` 指定次数循环执行（Loop）。

调试模式不通过本接口启动，应使用第 7 节的已保存工作流调试入口。

工作流必须已经成功保存并具有有效的 `ProgramHash`。旧 GraphData 数据需要先由系统迁移，正式运行不会在执行时临时解析 GraphData。

### 6.2 查询执行状态

```ts
const status = await getExecutionStatus(result.executionId)
```

```http
GET /api/app/workflow/executions/{executionId}?includeVariables=true
```

主要字段：

```ts
interface WorkflowExecutionStatus {
    executionId: string
    workflowId: string
    workflowName: string
    status: number
    error?: boolean
    errorCode?: string
    message?: string
    variables?: Array<Record<string, unknown>>
}
```

图像、点云和 Region 不直接作为大型 JSON 返回。响应只包含摘要或已有文件引用，实际数据继续通过平台现有图像、点云或文件接口访问。

## 7. 已保存工作流调试

### 7.1 页面状态

前端页面维护两个不同层次的状态：

1. 工作流编辑状态：未修改、未保存、保存中、已保存、保存失败。
2. 调试会话状态：未调试、启动中、已就绪、执行中、已暂停、已完成、失败、已停止或会话失效。

调试只运行最后一次成功保存的工作流。GraphData 有未保存修改时，“调试”按钮应提示
先保存，不能让用户误以为正在调试当前画布内容。

### 7.2 启动调试

```http
POST /api/app/workflow/{workflowId}/source/debug-run
Content-Type: application/json
```

```json
{
  "projectId": "项目 GUID",
  "loopCount": 1,
  "inputVariableKeys": [],
  "outputVariableNames": [],
  "breakpointNodeIds": ["画布节点 ID"]
}
```

该接口内部强制使用调试模式。前端不要传 `sourceCode`，也不要调用
`POST /api/app/workflow/source/debug`。

该接口在返回 `executionId` 后由服务端后台立即执行，不需要再调用一次“继续”。旧的
`/{workflowId}/source/debug` 仅为兼容保留，用于显式创建暂停在首节点前的会话。

“调试运行/继续（F5）”主按钮交互：

1. 校验已选择项目和工作流。
2. 若画布未保存，阻止启动并提示先保存。
3. 点击后立即显示“正在启动”，禁用重复启动。
4. 检查响应的 `error` 和 `executionId`。
5. `executionId` 为空或零 GUID 时视为启动失败，不能调用后续接口。
6. 成功后保存 `executionId`、加入 SignalR 执行分组并显示实时运行状态。
7. 命中断点后同一按钮显示“继续”；终态后再次点击会创建新会话。
8. 单步或运行到节点在未调试状态可以内部调用兼容创建接口，用户不需要单独创建会话。

### 7.3 调试状态模型

所有调试命令和状态查询都返回以下关键字段：

```ts
interface WorkflowDebugStatus {
    executionId: string
    workflowId: string
    workflowName: string
    debugState: 'ready' | 'running' | 'paused' | 'completed' | 'faulted' | 'stopped'
    isTerminal: boolean
    canContinue: boolean
    canStep: boolean
    canPause: boolean
    canStop: boolean
    currentNodeId?: string
    currentNodeName?: string
    currentNodeDurationMs: number
    faultNodeId?: string
    errorMessage?: string
    executedSteps: number
    totalSteps: number
    durationMs: number
    configuredOutputs: Array<{
        name: string
        displayName?: string
        valueType?: string
        hasValue: boolean
    }>
    outputs: Array<Record<string, unknown>>
    variables?: Array<Record<string, unknown>>
}
```

| `debugState` | 页面显示 | 允许操作 |
|---|---|---|
| `ready` | 已就绪，停在首节点前 | 继续、单步、运行到节点、停止 |
| `running` | 正在执行，显示动态蓝色状态 | 请求暂停、停止 |
| `paused` | 已暂停，黄色状态 | 继续、单步、运行到节点、停止 |
| `completed` | 执行完成，绿色状态 | 重新调试 |
| `faulted` | 执行失败，红色状态 | 查看错误、重新调试 |
| `stopped` | 已停止，灰色状态 | 重新调试 |

前端必须使用 `debugState` 和 `canContinue/canStep/canPause/canStop` 控制按钮，
不能通过 `currentNodeId` 或 `status` 数字推测是否完成。

点击继续、单步或运行到节点后，前端应立即进入本地 `running` 状态；收到接口响应或
SignalR 通知后，再以服务端 `debugState` 覆盖本地状态。状态栏同时显示
`executedSteps / totalSteps`。

### 7.4 调试命令

| 操作 | HTTP | 路径 | 请求体 |
|---|---|---|---|
| 单步 | POST | `/executions/{executionId}/steps` | `{"steps":1,"includeVariables":true}` |
| 继续 | POST | `/executions/{executionId}/continue` | 无 |
| 暂停 | POST | `/executions/{executionId}/pause` | 无 |
| 进入节点 | POST | `/executions/{executionId}/step-into` | 无 |
| 越过节点 | POST | `/executions/{executionId}/step-over` | 无 |
| 跳出工作流 | POST | `/executions/{executionId}/step-out` | 无 |
| 运行到节点 | POST | `/executions/{executionId}/run-to` | `{"nodeId":"..."}` |
| 停止 | DELETE | `/executions/{executionId}` | 无 |
| 查询状态 | GET | `/executions/{executionId}?includeVariables=true` | 无 |
| 查询完成结果 | GET | `/executions/{executionId}/result` | 无 |

上述路径均以 `/api/app/workflow` 为前缀。

当前运行时以算子节点为最小执行单位：

- 单步、进入节点和越过节点都会执行当前节点并停在下一节点。
- 暂停不能中断正在执行的同步算子，会在当前节点结束后生效。
- 跳出工作流在顶层表示运行剩余节点到结束。
- 继续运行到下一个断点；没有后续断点时运行到结束。

#### 7.4.1 查询完成结果

前端必须先通过状态机确认 `debugState === 'completed'`，再调用：

```http
GET /api/app/workflow/executions/{executionId}/result
```

成功响应直接是数组，不包含 `status`、内部变量、图片 URL、`error` 包装或
`stagedKey`：

```json
[
  {
    "name": "inspection_status",
    "displayName": "检测状态",
    "valueType": "bool",
    "value": true
  },
  {
    "name": "result_blob_key",
    "displayName": "结果文件",
    "valueType": "blob",
    "value": "workflow-results/2026/07/result.ply"
  }
]
```

| 字段 | 说明 |
|---|---|
| `name` | 结束节点勾选的运行时变量名称或变量路径 |
| `displayName` | 结束节点配置的 Display 名称；未填时等于 `name` |
| `valueType` | 运行时值类型 |
| `value` | 原生 JSON 值；文件类结果为 Blob Key |

`valueType` 是稳定令牌，只会使用 `int`、`long`、`float`、`double`、`decimal`、
`bool`、`string`、`blob`、`object`、`array`、`datetime`、`guid`；无法识别时回退为
`string`，不会返回 `System.Int32` 等 CLR 类型名。数值和布尔值均为原生 JSON 值。
布尔值在程序中仍按 `true/false` 判断，界面将 `true` 显示为绿色 `OK`，
将 `false` 显示为红色 `NG`。

文件结果的 `valueType` 为 `blob`；普通文本仍为 `string`。前端仅对 `blob` 值根据
Blob Key 最后一个路径段的扩展名（忽略大小写）选择展示方式：

| 分类 | 扩展名 | 展示 |
|---|---|---|
| 图片 | `.png/.jpg/.jpeg/.bmp/.webp/.tif/.tiff` | 图片预览 |
| 点云/3D | `.ply/.pcd/.xyz/.pts/.asc/.obj` | 3D 查看器 |
| 3D 模型 | `.stl/.glb/.gltf` | 3D 查看器 |
| CAD | `.step/.stp/.iges/.igs` | 文件信息和下载 |
| JSON | `.json` | 结构化查看 |
| 文本 | `.txt/.csv/.log` | 文本查看 |
| 其他 | 未知扩展名 | 文件信息和下载 |

`string` 即使以 `.png` 等扩展名结尾也按普通文本显示。`blob` 无扩展名时按普通文件
下载；有扩展名时，扩展名是文件子类型的唯一判断依据。不得使用变量名或 Display
名称猜测。Blob Key 必须
原样返回，不能替换成暂存 Key 或下载 URL。若结束节点直接绑定 `Mat` 或
`PointCloudData`，结果页提示“请先使用存 Blob 算子”，不尝试内嵌大型数据。

`faulted`、`stopped` 或尚未完成时不要请求结果接口；失败信息从状态接口的
`errorMessage` 读取。页面恢复到一个已完成会话时，也按同样顺序先确认状态再查结果。

### 7.5 结果页前端改动

结果页不得直接对 `value` 调用 `String(value)` 后统一显示。应先按 `valueType`
处理真实值类型，再仅对 `string` 值检查 Blob Key 扩展名：

```ts
type WorkflowResultValueType =
    | 'int' | 'long' | 'float' | 'double' | 'decimal'
    | 'bool' | 'string' | 'object' | 'array'
    | 'datetime' | 'guid'

type WorkflowResultPresentation =
    | 'boolean' | 'number' | 'text' | 'object' | 'array'
    | 'image' | 'point-cloud' | 'model-3d'
    | 'cad' | 'json-file' | 'text-file' | 'file'
    | 'unsupported-binary' | 'empty'
```

本项目对应实现：

| 文件 | 职责 |
|---|---|
| `src/utils/workflow-result.ts` | 从 Blob Key 最后一个路径段提取扩展名并完成展示分类 |
| `src/components/workflow/WorkflowBlobPreview.vue` | 使用鉴权请求获取 Blob，完成图片、文本及 3D 预览和下载 |
| `src/components/workflow/WorkflowJsonTree.vue` | 可折叠展示对象、数组和 `.json` 文件 |
| `src/views/workflow/WorkflowIdePage.vue` | 状态完成后查询结果，显示 OK/NG、类型、文件操作及原始数据提示 |

前端交互要求：

- `bool` 的原始值必须保留为 boolean；`true` 显示绿色 `OK`，`false` 显示红色
  `NG`，不得把 `"OK"`/`"NG"` 回写为接口值。
- 数值按 `valueType` 显示，不根据字符串内容猜测。
- `object`、`array` 和 `.json` 使用可折叠 JSON 树。
- 图片、点云和模型点击“查看”后，通过 Blob Key 调下载接口取得内容；Blob Key
  本身不是公开 URL，不能直接赋给 `<img src>`。
- CAD 和未知文件不自动下载，显示文件名、扩展名和下载按钮。
- `.ply/.pcd/.xyz/.pts/.asc/.obj/.stl/.glb/.gltf` 进入 3D 查看器。
- 原始 `Mat`、`PointCloudData` 不下载、不渲染，提示先通过存 Blob 算子输出 Key。
- 切换执行会话、重新调试或结果刷新时，必须清理旧预览、Object URL、WebGL
  Renderer、材质和几何体，防止显示上一次执行结果或产生显存泄漏。

结果查询时序：

```ts
const status = await getDebugStatus(executionId)
if (status.debugState === 'completed') {
    const results = await getDebugExecutionResult(executionId)
    renderWorkflowResults(results)
}
```

`running`、`paused`、`faulted`、`stopped` 状态均不得提前查询完成结果。

### 7.6 断点交互

```http
PUT /api/app/workflow/executions/{executionId}/breakpoints
```

```json
{
  "breakpoints": [
    {
      "nodeId": "画布节点 ID",
      "enabled": true
    }
  ]
}
```

建议交互：

- 单击节点只负责选中。
- 双击节点切换断点，或选中后点击“设置断点/取消断点”。
- 红色边框或红点表示断点，绿色高亮表示当前将要执行的节点。
- 断点在前端按工作流暂存；创建新调试会话后重新提交。
- PUT 是全量替换，必须提交当前完整断点集合。
- 删除节点时同步删除该节点的断点。

### 7.6 节点高亮与详情刷新

每次收到状态后：

1. 用 `currentNodeId` 找到 GraphData 节点。
2. 将当前节点居中并显示绿色执行标记。
3. `faulted` 时优先高亮 `faultNodeId`。
4. 刷新变量、调用栈、跟踪和性能列表。
5. `completed` 时保留最后结果，但取消“正在执行”动画。

详情接口：

| 数据 | HTTP | 路径 |
|---|---|---|
| 变量 | GET | `/executions/{executionId}/variables` |
| 调用栈 | GET | `/executions/{executionId}/stack` |
| 跟踪 | GET | `/executions/{executionId}/trace` |
| 性能 | GET | `/executions/{executionId}/performance` |
| 监视表达式 | POST | `/executions/{executionId}/watch` |
| 断点集合 | GET | `/executions/{executionId}/breakpoints` |

纯工作流页面可以只实现变量、跟踪和性能列表，不需要代码行定位。监视表达式只支持
变量名、属性和数组下标，不支持执行方法。

### 7.7 状态通知与轮询

SignalR Hub 为 `/signalr-hubs/workflow-debug`。连接后调用
`JoinExecutionAsync(executionId)`，监听 `DebugStateChangedAsync`。事件参数依次为
`executionId`、`eventType`、`updatedAt` 和完整状态摘要。

后端调试通知事件包括：

- `session-started`
- `node-started`
- `node-completed`
- `breakpoint-hit`
- `running`
- `paused`
- `pause-requested`
- `stop-requested`
- `session-completed`
- `session-faulted`
- `session-stopped`

已接入 SignalR 时优先根据通知更新；仍建议在网络重连或页面恢复可见时调用状态查询
校准一次。未接入 SignalR 时，可在 `running` 状态每 500～1000ms 查询一次，进入
`paused/completed/faulted/stopped` 后停止轮询。

不要在 `paused` 状态持续轮询，也不要同时启动多个状态轮询定时器。

### 7.8 页面刷新与会话恢复

进入工作流页面、浏览器刷新或切换当前工作流后，前端必须先查询项目现有调试会话：

```http
GET /api/app/workflow/executions?projectId={projectId}&includeVariables=true
```

恢复流程：

1. 取得当前 `projectId` 和 `workflowId`。
2. 查询项目调试会话列表。
3. 仅保留 `workflowId` 与当前工作流相同的会话。
4. 优先恢复 `isTerminal=false` 的活动会话；没有活动会话时可以展示最近的终态结果。
5. 保存响应中的 `executionId` 和完整状态。
6. 调用 `GET /executions/{executionId}/breakpoints` 恢复画布断点。
7. 使用 `currentNodeId` 或 `faultNodeId` 恢复节点高亮。
8. 刷新变量、调用栈、跟踪和性能列表。
9. 按 `debugState` 和 `can*` 字段恢复状态栏及按钮。

查询期间页面显示“正在恢复调试状态”，不要同时创建新调试会话。若没有匹配会话，
页面进入“未调试”状态。若查询返回“执行会话不存在”，清除本地 `executionId` 和
断点会话关联；前端可以保留用户配置的断点草稿，待下次启动后重新提交。

调试会话保存在服务端内存中，所以同一服务进程内刷新页面可以恢复；服务重启或会话
超过 TTL 后无法恢复，必须重新启动调试。

### 7.9 完成、失败与会话失效

- `completed`：自动切换“结果”面板，展示耗时、进度和 `outputs`；主按钮变为“调试运行”。
- `faulted`：显示 `faultNodeId` 和 `errorMessage`，禁止继续旧会话。
- `stopped`：清空活动 `executionId`，保留“已停止”提示。
- 服务重启、会话超时或返回“执行会话不存在”：标记为“会话失效”，清空
  `executionId`，提示用户重新点击调试。
- 页面切换工作流前，若存在非终态会话，应先询问是否停止；确认后调用 DELETE。
- 页面卸载时不要静默启动新会话，也不要用零 GUID 调用任何调试接口。

### 7.10 推荐按钮状态

| 页面状态 | 主按钮（F5） | 暂停 | 单步 | 运行到节点 | 停止 |
|---|---:|---:|---:|---:|---:|
| 未保存修改 | 禁用 | 禁用 | 禁用 | 禁用 | 视旧会话而定 |
| 未调试 | 调试运行 | 禁用 | 启用 | 选中节点时启用 | 禁用 |
| `ready/paused` | 继续 | 禁用 | 启用 | 选中节点时启用 | 启用 |
| `running` | 禁用 | 启用 | 禁用 | 禁用 | 启用 |
| `completed/faulted/stopped` | 调试运行 | 禁用 | 启用 | 选中节点时启用 | 禁用 |

## 10. 错误处理

### 10.1 常见状态码

| 状态码 | 处理建议 |
|---|---|
| `400` | 请求字段、GraphData 或工作流校验失败，显示服务端诊断 |
| `401/403` | 登录状态或权限不足 |
| `404` | 工作流、运行或部署不存在 |
| `409` | 数据已被修改或无法安全合并，重新加载最新工作流 |
| `500` | 服务端执行故障，记录 `errorCode` 和 `message` |

### 10.2 运行限制错误码

| 错误码 | 说明 |
|---|---|
| `WORKFLOW_TIMEOUT` | 工作流总执行时间超限 |
| `WORKFLOW_NODE_TIMEOUT` | 单节点执行时间超限 |
| `WORKFLOW_LOOP_LIMIT` | 循环次数超过配置上限 |
| `WORKFLOW_OUTPUT_TOO_LARGE` | 普通结构化输出超过大小限制 |
| `WORKFLOW_PROJECT_QUOTA` | 本机项目调试会话达到上限，应停止旧会话后重试 |

第三方调用 CRUD 接口通常不会提交并发戳。若后续接入带修订号的内部编辑接口，HTTP 409 响应会附带：

```json
{
  "serverRevision": 12,
  "contentHash": "...",
  "semanticHash": "...",
  "programHash": "..."
}
```

收到 409 后应重新调用 `getWorkflow(id)`，不得自动覆盖服务端版本。
