# 用户、角色与菜单权限前端对接文档

> 适用项目：AuroraStruct3D Frontend  
> 文档日期：2026-08-29  
> 接口风格：JSON + Bearer JWT，字段使用 camelCase

## 1. 对接范围

本文档覆盖：

- 用户名密码登录、Token 保存及应用权限初始化；
- 访客、操作员、管理员三级菜单和路由权限；
- 用户分页、创建、编辑、删除、启停、重置密码及角色分配；
- 角色分页、创建、编辑、删除；
- 获取、保存角色或用户的权限树；
- 401、403 和 ABP 标准错误响应处理。

项目中已有可直接复用的前端封装：

- `src/api/auth.ts`：登录接口；
- `src/api/abp-application.ts`：当前用户及授权策略；
- `src/api/management.ts`：用户、角色、权限接口；
- `src/stores/auth.ts`：Token、当前用户和权限状态；
- `src/auth/access-control.ts`：访问级别判定。

## 2. 权限模型

| 用户类型 | 登录状态 | 后端角色 | 应用权限 | 前端能力 |
| --- | --- | --- | --- | --- |
| 访客 | 未登录 | 无 | 无 | 只能进入登录页 |
| 操作员 | 已登录 | `operator` | `AuroraStruct3D.Access.Operation` | 业务菜单和业务操作 |
| 管理员 | 已登录 | `admin` | Operation + Management，并拥有细粒度管理权限 | 操作员全部能力及系统管理能力 |
| 受限账号 | 已登录 | 自定义角色或角色配置不完整 | 无 Operation/Management | 跳转 403，不应显示业务菜单 |

应用级权限常量：

```ts
const AppPermissions = {
    operation: 'AuroraStruct3D.Access.Operation',
    management: 'AuroraStruct3D.Access.Management',
} as const
```

注意：管理员是前端访问级别的最高层级，因此具有 `management` 时前端同时允许访问操作员菜单。但后端的 Operation 和 Management 是两个独立策略，管理员角色应同时授予二者。

系统默认公开角色为 `operator`；`admin` 不再是默认角色，避免支持默认角色的注册流程自动赋予管理权限。通过管理接口创建用户时，前端仍应明确提交 `roleNames: ["operator"]`。

## 3. 请求约定

### 3.1 基础地址

生产环境推荐前后端同源，请求地址以 `/` 为基础地址。

管理接口使用显式路由，例如：

```text
POST /Users/page
POST /Roles/page
POST /Permissions/tree
```

登录和 ABP 应用配置使用：

```text
POST /api/app/account/login
POST /api/app/account/refresh-token
GET  /api/abp/application-configuration
```

### 3.2 通用请求头

```http
Authorization: Bearer <access-token>
Content-Type: application/json
Accept-Language: zh-CN
__tenant: <tenant-id>                # 多租户场景可选
X-Client-Session-Id: <tab-session-id> # 设备操作接口使用
```

- 登录接口不需要 `Authorization`；
- 刷新 Token 时不要携带过期的 Access Token；
- 租户登录时，将租户 ID 放在 `__tenant` 请求头，不放在登录 JSON 中；
- 所有 GUID 在前端均按 `string` 处理。

### 3.3 分页请求和响应

分页从 `pageIndex = 1` 开始：

```json
{
  "pageIndex": 1,
  "pageSize": 20,
  "filter": "admin",
  "sorting": "creationTime desc"
}
```

标准分页响应：

```json
{
  "items": [],
  "totalCount": 0
}
```

## 4. 登录与权限初始化

### 4.1 登录

`POST /api/app/account/login`

请求体：

```json
{
  "name": "admin",
  "password": "******"
}
```

`name` 支持用户名或邮箱。

响应示例：

```json
{
  "id": "7f71b69e-3f34-4f07-93e7-f4756fdd9092",
  "name": "Administrator",
  "userName": "admin",
  "token": "eyJ...",
  "refreshToken": "...",
  "roles": ["admin"]
}
```

登录成功后先保存 `token`，随后必须获取应用配置。菜单权限不要只依据登录响应里的角色名判断。

### 4.2 获取当前用户和授权策略

`GET /api/abp/application-configuration`

关键响应字段：

```json
{
  "currentUser": {
    "isAuthenticated": true,
    "id": "7f71b69e-3f34-4f07-93e7-f4756fdd9092",
    "userName": "admin",
    "roles": ["admin"]
  },
  "currentTenant": {
    "id": null,
    "name": null,
    "isAvailable": false
  },
  "auth": {
    "grantedPolicies": {
      "AuroraStruct3D.Access.Operation": true,
      "AuroraStruct3D.Access.Management": true,
      "AbpIdentity.Users": true,
      "AbpIdentity.Roles": true
    }
  }
}
```

权限配置加载成功后，`auth.grantedPolicies` 是前端按钮、菜单和路由判定的唯一可信来源。JWT 角色仅用于应用配置暂时不可用时的降级显示。

推荐初始化顺序：

```ts
const loginResult = await loginAsync({ username, password, tenantId })
auth.setToken(loginResult.token)
auth.setTenantId(tenantId ?? null)

const config = await getApplicationConfigurationAsync()
auth.setCurrentUser({
    id: config.currentUser.id ?? '',
    userName: config.currentUser.userName ?? '',
    email: config.currentUser.email,
    tenantId: config.currentUser.tenantId,
    roles: config.currentUser.roles ?? [],
})
auth.setGrantedPolicies(config.auth.grantedPolicies)
```

### 4.3 刷新 Token

`POST /api/app/account/refresh-token`

请求体：

```json
{
  "userId": "7f71b69e-3f34-4f07-93e7-f4756fdd9092",
  "refreshToken": "..."
}
```

响应：

```json
{
  "success": true,
  "message": "Success",
  "token": "eyJ...",
  "refreshToken": "..."
}
```

刷新成功后必须同时替换 Access Token 和 Refresh Token，并重新获取应用配置。刷新接口当前尚未在 `src/api/auth.ts` 中完成自动续期接入，如前端暂不实现续期，收到 401 后清理本地认证状态并回到登录页。

## 5. 菜单与路由控制

### 5.1 菜单分组

| 菜单 | 最低访问级别 |
| --- | --- |
| 仪表盘、视觉方案 | 操作员 |
| 故障历史、状态日志 | 操作员 |
| 投影仪、相机、串口、电机、PLC | 操作员 |
| 三维数模、AI 模型、标定管理 | 操作员 |
| 工作流调试 | 管理员 |
| Swagger、CAP、Hangfire、MiniProfiler、系统信息 | 管理员 |
| 用户管理、角色管理、权限配置 | 管理员 |

未登录时不渲染主布局菜单，直接进入登录页。

### 5.2 菜单判定

```vue
<Button v-if="auth.canOperate">业务菜单</Button>
<Button v-if="auth.canManage">管理菜单</Button>
```

不要只隐藏菜单。所有受控页面还必须配置路由权限：

```ts
{
    path: 'projects',
    component: () => import('@/views/projects/ProjectManagePage.vue'),
    meta: { requiresAuth: true, access: AccessLevel.operator },
}

{
    path: 'system/users',
    component: () => import('@/views/system/UserPage.vue'),
    meta: { requiresAuth: true, access: AccessLevel.administrator },
}
```

路由守卫行为：

1. `requiresAuth` 且未登录：跳转 `/login?redirect=<原地址>`；
2. 已登录但权限配置未加载：先调用 application-configuration；
3. 权限不足：跳转 `/forbidden`；
4. 登录成功：返回原 `redirect` 地址。

### 5.3 按钮级权限

管理页面中的操作按钮还应检查细粒度权限：

```ts
function hasPolicy(name: string): boolean {
    return auth.grantedPolicies[name] === true
}
```

常用策略：

| 功能 | 策略名称 |
| --- | --- |
| 查看用户 | `AbpIdentity.Users` |
| 创建用户 | `AbpIdentity.Users.Create` |
| 编辑用户 | `AbpIdentity.Users.Update` |
| 删除用户 | `AbpIdentity.Users.Delete` |
| 分配用户角色 | `AbpIdentity.Users.Update.ManageRoles` |
| 配置用户权限 | `AbpIdentity.Users.ManagePermissions` |
| 启停用户 | `AbpIdentity.Users.Enable` |
| 重置密码 | `AbpIdentity.Users.ResetPassword` |
| 查看角色 | `AbpIdentity.Roles` |
| 创建角色 | `AbpIdentity.Roles.Create` |
| 编辑角色 | `AbpIdentity.Roles.Update` |
| 删除角色 | `AbpIdentity.Roles.Delete` |
| 配置角色权限 | `AbpIdentity.Roles.ManagePermissions` |

即使按钮未隐藏，后端仍会校验这些策略并返回 403。

## 6. 用户管理接口

### 6.1 接口总览

| 功能 | 方法与地址 | 请求体 | 返回值 |
| --- | --- | --- | --- |
| 用户分页 | `POST /Users/page` | `PageInput` | `PagedResult<UserDto>` |
| 创建用户 | `POST /Users/create` | `CreateUserInput` | `UserDto` |
| 更新用户 | `POST /Users/update` | `{ userId, userInfo }` | `UserDto` |
| 删除用户 | `POST /Users/delete` | `{ id }` | 空 |
| 获取用户角色 | `POST /Users/role` | `{ id }` | `{ items: RoleDto[] }` |
| 更新用户角色 | `POST /Users/roles/update` | `{ userId, roleNames }` | 空 |
| 启用或禁用 | `POST /Users/setActive` | `{ userId, isActive }` | 空 |
| 重置密码 | `POST /Users/resetPassword` | `{ userId, password }` | `boolean` |

### 6.2 创建用户

```json
{
  "userName": "operator01",
  "name": "操作员一",
  "surname": null,
  "email": "operator01@example.com",
  "phoneNumber": null,
  "password": "******",
  "isActive": true,
  "lockoutEnabled": true,
  "roleNames": ["operator"]
}
```

管理端创建用户时必须明确传入 `roleNames`，默认选择 `["operator"]`。不要依赖角色的 `isDefault` 属性自动分配；若传空数组或不传角色，新账号可能没有可登录的业务角色。

### 6.3 更新用户

```json
{
  "userId": "f59bf7e5-135d-4cf9-825b-71dff9d12502",
  "userInfo": {
    "userName": "operator01",
    "name": "操作员一",
    "surname": null,
    "email": "operator01@example.com",
    "phoneNumber": null,
    "isActive": true,
    "lockoutEnabled": true,
    "roleNames": ["operator"],
    "concurrencyStamp": "当前列表或详情返回的 concurrencyStamp"
  }
}
```

编辑时保留并回传 `concurrencyStamp`，用于并发更新检查。

### 6.4 启停用户

```json
{
  "userId": "f59bf7e5-135d-4cf9-825b-71dff9d12502",
  "isActive": false
}
```

`isActive = false` 表示禁用。历史 `/Users/lock` 接口字段语义容易混淆，新前端统一使用 `/Users/setActive`。

### 6.5 分配角色

先获取当前角色：

```http
POST /Users/role

{ "id": "f59bf7e5-135d-4cf9-825b-71dff9d12502" }
```

再覆盖保存角色名称：

```http
POST /Users/roles/update

{
  "userId": "f59bf7e5-135d-4cf9-825b-71dff9d12502",
  "roleNames": ["operator"]
}
```

`roleNames` 使用角色名称，不使用角色 ID。传空数组会移除用户的全部非静态角色，保存前应进行二次确认。

## 7. 角色管理接口

### 7.1 接口总览

| 功能 | 方法与地址 | 请求体 | 返回值 |
| --- | --- | --- | --- |
| 角色分页 | `POST /Roles/page` | `PageInput` | `PagedResult<RoleDto>` |
| 全部角色 | `POST /Roles/all` | `{}` | `{ items: RoleDto[] }` |
| 创建角色 | `POST /Roles/create` | `CreateRoleInput` | `RoleDto` |
| 更新角色 | `POST /Roles/update` | `{ roleId, roleInfo }` | `RoleDto` |
| 删除角色 | `POST /Roles/delete` | `{ id }` | 空 |

### 7.2 创建角色

```json
{
  "name": "quality-inspector",
  "isDefault": false,
  "isPublic": true
}
```

### 7.3 更新角色

```json
{
  "roleId": "80327b57-a92f-461b-8d7d-e339be444857",
  "roleInfo": {
    "name": "quality-inspector",
    "isDefault": false,
    "isPublic": true,
    "concurrencyStamp": "当前角色返回的 concurrencyStamp"
  }
}
```

`isStatic = true` 的系统角色不允许前端删除。`admin` 不应设置为默认角色；一般业务账号应使用 `operator` 或其他仅具 Operation 权限的角色。

## 8. 权限树接口

### 8.1 Provider 规则

| 授权对象 | `providerName` | `providerKey` |
| --- | --- | --- |
| 角色 | `R` | 角色名称，例如 `operator`，不是角色 ID |
| 用户 | `U` | 用户 ID 字符串 |

后端只接受 `R` 或 `U`，其他值返回 400。

### 8.2 获取权限树

`POST /Permissions/tree`

角色示例：

```json
{
  "providerName": "R",
  "providerKey": "operator"
}
```

响应示例：

```json
{
  "grants": [
    "AuroraStruct3D.Access",
    "AuroraStruct3D.Access.Operation"
  ],
  "allGrants": [
    "AuroraStruct3D.Access.Operation",
    "AuroraStruct3D.Access.Management"
  ],
  "permissions": [
    {
      "key": "AuroraStruct3D.Access",
      "title": "应用访问权限",
      "children": [
        {
          "key": "AuroraStruct3D.Access.Operation",
          "title": "操作权限",
          "children": []
        },
        {
          "key": "AuroraStruct3D.Access.Management",
          "title": "管理权限",
          "children": []
        }
      ]
    }
  ]
}
```

- `permissions`：用于渲染树；
- `grants`：当前已选节点，可能包含仅用于树展示的分组 key；
- `allGrants`：所有可保存的真实权限名称。

### 8.3 保存权限

`POST /Permissions/update`

请求结构：

```json
{
  "providerName": "R",
  "providerKey": "operator",
  "updatePermissionsDto": {
    "permissions": [
      {
        "name": "AuroraStruct3D.Access.Operation",
        "isGranted": true
      },
      {
        "name": "AuroraStruct3D.Access.Management",
        "isGranted": false
      }
    ]
  }
}
```

保存时应遍历 `allGrants` 生成完整数组：

```ts
const checked = new Set(checkedPermissionKeys)
const permissions = result.allGrants.map((name) => ({
    name,
    isGranted: checked.has(name),
}))

await updatePermissionsAsync({
    providerName: PermissionProvider.Role,
    providerKey: role.name!,
    permissions,
})
```

不要只提交已勾选项，否则未提交项不保证被撤销；也不要把不在 `allGrants` 中的分组 key 当作真实权限提交。

权限变更后：

- 被修改用户应重新获取 application-configuration；
- 如果修改的是当前用户角色权限，建议刷新权限配置或重新登录；
- 前端不得长期缓存旧的 `grantedPolicies`。

## 9. 推荐的前端页面流程

### 9.1 用户管理页

1. 调用 `/Users/page` 加载列表；
2. 根据细粒度策略显示创建、编辑、删除、启停、重置密码按钮；
3. 打开角色弹窗时并行请求 `/Roles/all` 和 `/Users/role`；
4. 使用角色名称作为多选值；
5. 保存到 `/Users/roles/update` 后刷新该行；
6. 禁止当前管理员在无确认的情况下禁用或删除自己。

### 9.2 角色管理页

1. 调用 `/Roles/page` 加载角色；
2. 静态角色隐藏或禁用删除按钮；
3. 点击“权限配置”时，以角色名称调用 `/Permissions/tree`；
4. 权限树勾选状态取 `grants`，保存集合取 `allGrants`；
5. 保存后重新读取权限树，确认后端实际授权结果。

## 10. 错误处理

ABP 业务错误通常返回：

```json
{
  "error": {
    "code": "业务错误码",
    "message": "可展示给用户的错误信息",
    "details": "详细信息",
    "validationErrors": [
      {
        "message": "字段校验失败",
        "members": ["userName"]
      }
    ]
  }
}
```

状态码处理建议：

| 状态码 | 前端处理 |
| --- | --- |
| 400 | 展示 `error.message`，表单场景同步展示 validationErrors |
| 401 | 清空 Token 和当前用户，跳转登录并保留 redirect |
| 403 | 提示无操作权限；页面导航场景进入 `/forbidden` |
| 404 | 提示资源不存在并刷新列表 |
| 409 | 提示数据已被其他用户修改，重新加载最新数据 |
| 500/502/503 | 统一服务异常提示，避免展示 HTML 响应体 |

## 11. 前端验收清单

- [ ] 未登录访问业务 URL 会跳转登录页；
- [ ] 登录后会请求 application-configuration；
- [ ] `operator` 只显示业务菜单；
- [ ] `admin` 同时显示业务菜单和管理菜单；
- [ ] 已登录但没有 Operation/Management 时进入 403；
- [ ] 直接输入管理 URL 时仍会经过路由权限校验；
- [ ] 用户启停统一使用 `/Users/setActive`；
- [ ] 用户角色保存传角色名称数组；
- [ ] 角色权限请求的 `providerKey` 使用角色名称；
- [ ] 权限保存覆盖提交 `allGrants` 中的每个权限；
- [ ] 用户、角色按钮按细粒度策略显示；
- [ ] 401 会清理登录状态，403 不会误清理 Token；
- [ ] 权限修改后能刷新当前用户的菜单和路由状态。
